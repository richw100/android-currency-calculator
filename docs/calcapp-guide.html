1. What We Built and Why

CalcApp is an Android calculator that shows the result of every calculation in two currencies simultaneously — a "from" currency (whatever you're spending in) and a "to" currency (whatever you want to see the equivalent in). As you type, both values update in real time.

The from/to framing is deliberately direction-neutral: it works equally well when you're travelling abroad (from GBP to local currency) or planning a holiday at home (from EUR prices to GBP cost).

Key features:

  • Standard 4-function calculator (+, −, ×, ÷)
  • Bracket support — sub-expressions like (10 + 5) × 3
  • Smart bracket button that opens or closes depending on context
  • Percentage button — converts the current number to a decimal fraction
  • Exchange rates fetched from a free public API (open.er-api.com)
  • Rates cached locally for 24 hours so the app works offline
  • Manual refresh button with a live spinner
  • Exchange rate label showing full currency names and the current cross-rate
  • Swap button to instantly reverse the from/to currencies
  • Currency selection remembered between app launches
  • Receipt scanner — ML Kit OCR reads prices from a photo; tap any number to overlay its converted value directly on top of the original; multi-select builds a running total
  • Card fee profiles — named profiles with per-cent fee, minimum charge, and per-card exchange rate overrides
  • Tip calculator with bill splitting and FX hand-off
  • Local Info screen — emergency numbers, calling codes, currency, languages, driving side, speed limits (mph or km/h), BAC limit, tap water safety, plug type/voltage for 80+ countries
  • Unit converters: distance, volume, weight, speed, pressure, energy, temperature, fuel economy, clothing and shoe sizes

The Android SDK

The Android SDK (installed at ~/android) contains:

  • platform-tools — includes adb
  • build-tools — aapt2 (resource compiler), d8 (DEX compiler), apksigner
  • platforms/android-35 — the Android 35 API stubs (like a header-only SDK)

What is an APK?

An APK is just a ZIP file. If you rename app-debug.apk to app-debug.zip and unzip it you'll find:

  • classes.dex — compiled bytecode (like a .pyc, but for Android's runtime)
  • resources.arsc — compiled resources (strings, layouts)
  • AndroidManifest.xml — binary-encoded manifest
  • lib/ — native .so files if any
  • META-INF/ — signing certificates

4. Gradle: The Build System

Gradle is a JVM-based build system using a Kotlin DSL (domain-specific language). It replaces CMake and pip in one tool.

The Gradle wrapper

The gradlew script does not require Gradle to be installed globally. It reads gradle-wrapper.properties to find the required version, downloads it from Gradle's servers on first run, and caches it in ~/.gradle/wrapper/dists/. This guarantees everyone builds with exactly the same Gradle version — equivalent to pinning a CMake version in CI.

Version catalogue: gradle/libs.versions.toml

This file centralises all library versions in one place:

[versions]
kotlin = "2.0.20"
retrofit = "2.11.0"

[libraries]
retrofit = { group = "com.squareup.retrofit2", name = "retrofit", version.ref = "retrofit" }
# material-icons-extended is needed for icons like SwapHoriz not in the core set
androidx-compose-material-icons = { group = "androidx.compose.material", name = "material-icons-extended" }

[plugins]
kotlin-android = { id = "org.jetbrains.kotlin.android", version.ref = "kotlin" }

Dependencies are then referenced in build.gradle.kts as libs.retrofit rather than hard-coded strings. This is equivalent to defining version variables in a top-level CMakeLists and find_package() elsewhere.

material-icons-core vs material-icons-extended: Compose ships two icon sets. The core set is small but only contains the most common icons. SwapHoriz (used for the currency swap button) is in extended only. Using the wrong set causes an "unresolved reference" compile error even though the icon name looks correct.

The app's build.gradle.kts

The important sections:

android {
    compileSdk = 35         // The API level you compile against (like -I/path/to/sdk/headers)
    defaultConfig {
        minSdk = 26         // Oldest Android version the app runs on (Android 8.0, ~95% of devices)
        targetSdk = 35      // Tells Android which behaviour version you've tested against
    }
    buildFeatures {
        compose = true      // Enable the Compose compiler plugin
    }
}
compileSdk vs minSdk: compileSdk is what you build against (the headers). minSdk is the minimum runtime version. If you call an API added in SDK 30 without a version check, the build will warn but the app will crash at runtime on SDK 26 devices.

How dependencies are resolved

Android libraries are published to Maven Central and Google's Maven repository — like PyPI but for JVM packages. Gradle downloads them to ~/.gradle/caches/ on first build. The format group:name:version maps to a URL path on the repository server.

5. Kotlin: The Language

Kotlin compiles to JVM bytecode and runs on Android's runtime (ART). If you know Python well and have written C, Kotlin will feel familiar with a few new concepts.

Key syntax for reading the codebase

Data classes (like C structs with free equality/copy)

data class CalculatorUiState(
    val display: String = "0",     // val = immutable (const), var = mutable
    val isError: Boolean = false   // default values like Python keyword args
)

The data keyword auto-generates equals(), hashCode(), toString(), and a copy() method.

Sealed classes (like a typed union / enum with data)

sealed class CalculatorAction {
    data class Digit(val value: Int) : CalculatorAction()
    object Clear : CalculatorAction()   // object = singleton instance
}

A sealed class has a fixed set of subtypes known at compile time. The compiler can then enforce exhaustive when matching — like a C enum in a switch but carrying data.

Coroutines (like async/await in Python)

viewModelScope.launch {          // starts a coroutine (like asyncio.create_task)
    val rates = repository.getRates()   // suspend fun — yields while waiting, like await
    updateDisplay()
}

Coroutines are Kotlin's concurrency primitive. suspend fun is like Python's async def. They run on a thread pool managed by the coroutine dispatcher.

Extension functions

// Adds a .dataStore property to any Context object
private val Context.dataStore: DataStore<Preferences>
    by preferencesDataStore(name = "exchange_rates")

Extension functions add methods to existing classes without subclassing. The by keyword here is Kotlin's property delegation.

Lambda syntax

rates.keys.filter { it.contains(search, ignoreCase = true) }
//                 ^^^  'it' is the implicit single parameter, like Python's lambda x: ...

Null safety

val rate: Double? = rates["GBP"]   // ? means nullable (can be null)
val rate: Double  = rates["GBP"]!! // !! asserts non-null (throws if null — avoid in prod)
rate?.let { doSomething(it) }      // safe call — only runs if rate != null

The compiler enforces null safety at compile time. This eliminates an entire class of null-pointer crashes.

6. Jetpack Compose: The UI Framework

Compose is a declarative UI framework — you describe what the UI should look like given the current state, and Compose figures out what to redraw when state changes.

Mental model: Think of it like a function that maps state → pixels. Every time state changes, Compose re-calls the affected @Composable functions and diffs the result, updating only what changed. This is similar to how React works in the web world.

Composable functions

Any function annotated with @Composable can emit UI elements:

@Composable
fun CalcButton(label: String, onClick: () -> Unit) {
    Button(onClick = onClick) {
        Text(text = label)
    }
}

These are not widgets you instantiate — they're functions you call. Compose tracks which composables depend on which state and only re-executes the ones that need to change.

State and recomposition

val state by vm.uiState.collectAsStateWithLifecycle()
// 'by' delegates property access to the StateFlow collector
// Whenever uiState emits a new value, the composable recomposes

StateFlow is a stream that always has a current value — like an observable variable. collectAsStateWithLifecycle() subscribes to it and triggers recomposition on change.

Layout primitives

ComposeEquivalent
ColumnVertical stack (CSS flexbox column)
RowHorizontal stack (CSS flexbox row)
BoxOverlapping children (CSS position: relative)
Modifier.weight(1f)flex: 1 — takes proportional space
Modifier.fillMaxWidth()width: 100%
Spacer(Modifier.weight(1f))Pushes siblings apart (like CSS justify-content: space-between)

ViewModel: separating state from UI

The ViewModel is a lifecycle-aware class that survives screen rotations. It holds all mutable state and business logic. The Compose UI reads from it but never writes directly — it only sends CalculatorAction events down to the ViewModel. This is the MVVM (Model-View-ViewModel) pattern:

UI (CalculatorScreen) ──actions──▶ ViewModel ──uiState──▶ UI
                                       │
                                   Repository
                                       │
                                 API / DataStore

7. Every File Explained

AndroidManifest.xml

The app's declaration — read by Android's package manager when installing. Declares:

  • INTERNET permission — required to make HTTP requests
  • The MainActivity as the launcher activity (what opens when you tap the icon)
  • The app's theme, label, and other metadata

Without android:exported="true" on the main activity, the launcher can't start it. Without the INTERNET permission, any network call will fail silently.

MainActivity.kt

The entry point. In Android, there is no main() function — the OS calls onCreate() on the declared launcher Activity. Ours does three things:

  1. enableEdgeToEdge() — lets the app draw behind the system bars
  2. setContent { } — hands control to Compose, replacing the traditional XML inflation step
  3. Wraps everything in CalcAppTheme so Material3 colours apply everywhere

ui/theme/Theme.kt

Sets up Material3's colour system. On Android 12+ it uses dynamic colour — the system extracts a palette from the user's wallpaper. On older versions it falls back to the default Material3 palette. The isSystemInDarkTheme() call picks light or dark automatically.

data/ExchangeRateApi.kt

Two things in one file:

The response model — a data class Retrofit deserialises the JSON into:

data class ExchangeRateResponse(
    val result: String,
    @SerializedName("base_code") val baseCode: String,  // JSON key ≠ Kotlin name
    val rates: Map<String, Double>  // e.g. {"GBP": 0.79, "EUR": 0.92, ...}
)

The API interface — Retrofit generates an implementation at runtime from this interface:

interface ExchangeRateApi {
    @GET("v6/latest/{base}")            // HTTP GET, {base} is a path parameter
    suspend fun getRates(@Path("base") base: String): ExchangeRateResponse
}

Calling api.getRates("USD") makes a GET request to https://open.er-api.com/v6/latest/USD and returns the deserialised response. The suspend keyword means it runs asynchronously without blocking.

data/ExchangeRateRepository.kt

The data layer — responsible for answering "give me the rates" regardless of whether they come from the network or the cache.

DataStore is Android's key-value store (replacing SharedPreferences). It's backed by a file and accessed via coroutines. We use it to persist:

  • The JSON string of cached rates (RATES_KEY)
  • The timestamp of the last fetch (TIMESTAMP_KEY)
  • The base currency used for the cached rates (BASE_KEY, always "USD")
  • The user's selected to/from currencies (HOME_CURRENCY_KEY, LOCAL_CURRENCY_KEY)

Cache logic — getRates(baseCurrency, forceRefresh):

val cacheValid = !forceRefresh
    && cachedJson != null
    && cachedBase == baseCurrency
    && System.currentTimeMillis() - timestamp < 24h

if (cacheValid) return deserialise(cachedJson)

try {
    val response = api.getRates(baseCurrency)
    saveToCache(response)
    return response.rates
} catch (e: Exception) {
    if (cachedJson != null) return deserialise(cachedJson)  // graceful offline fallback
    else throw e  // no cache, no network — propagate the error
}

The forceRefresh = true path is taken when the user taps the refresh button. The normal startup path passes forceRefresh = false so cached rates are used if they are less than 24 hours old.

Currency preference persistence:

suspend fun saveCurrencyPrefs(home: String, local: String)
suspend fun loadCurrencyPrefs(): Pair<String, String>  // defaults: "EUR" to, "GBP" from

These are called every time the user changes or swaps currencies, so the selection is restored on next launch.

ui/CalculatorViewModel.kt

The core of the app. Holds all mutable state as a single CalculatorUiState emitted via a StateFlow.

CalculatorUiState

Everything the UI needs in one immutable snapshot:

CalculatorAction

Every button press is modelled as a sealed class instance sent to onAction(). The UI never mutates state directly.

    object Clear : CalculatorAction()            // AC

    object Calculate : CalculatorAction()        // =
    object Percent : CalculatorAction()          // % — divides current number by 100
    object SmartBracket : CalculatorAction()     // context-aware ( or )
    object OpenBracket : CalculatorAction()      // always opens a bracket
    object CloseBracket : CalculatorAction()     // always closes a bracket
    object RefreshRates : CalculatorAction()     // force a new network fetch
    object SwapCurrencies : CalculatorAction()   // swap from ↔ to
    data class Operation(val symbol: Char) : CalculatorAction()    // +, -, *, /
    data class SetToCurrency(val code: String) : CalculatorAction()
    data class SetFromCurrency(val code: String) : CalculatorAction()
}

Bracket stack architecture

Supporting nested sub-expressions requires more than two operand variables. The solution is a stack. Each time an opening bracket is pressed, the outer expression context (the left-hand value and pending operator) is saved on the stack. When a closing bracket is pressed, the inner expression is resolved and the outer context is restored.

// Represents the outer expression state frozen when ( was pressed
private data class BracketState(val firstOperand: Double?, val pendingOp: Char?)

private val bracketStack = mutableListOf<BracketState>()

Opening a bracket (handleOpenBracket):

bracketStack.add(BracketState(firstOperand, pendingOp))
firstOperand = null
pendingOp = null
currentInput = "0"
expressionDisplay.append("(")

Closing a bracket (handleCloseBracket):

// 1. Resolve the inner expression
val bracketResult = if (firstOperand != null && pendingOp != null)
    applyOp(firstOperand!!, currentInput.toDouble(), pendingOp!!)
else currentInput.toDouble()
expressionDisplay.append("$currentInput)")

// 2. Restore the outer context
val (outerFirst, outerOp) = bracketStack.removeLast()
firstOperand = outerFirst; pendingOp = outerOp

// 3. Apply the outer operator to the bracket result
val result = if (firstOperand != null && pendingOp != null)
    applyOp(firstOperand!!, bracketResult, pendingOp!!)
else bracketResult

firstOperand = result; pendingOp = null
currentInput = formatResult(result)
shouldResetInput = true

Smart bracket button

The ( ) button is context-aware — it opens or closes depending on what's happening:

is CalculatorAction.SmartBracket -> {
    val atStart = firstOperand == null && pendingOp == null
        && currentInput == "0" && bracketStack.isEmpty() && !justCalculated
    if (shouldResetInput || atStart) handleOpenBracket()
    else if (bracketStack.isNotEmpty()) handleCloseBracket()
    // else: mid-number entry with no open bracket — do nothing
}

shouldResetInput is true after an operator is pressed (the next input starts a new operand). That's also the right moment to open a bracket. If there are open brackets and we're part-way through entering a number, the button closes the innermost bracket.

Expression display

The small grey line above the main number (e.g. 12 + (34 ×) is driven by a StringBuilder maintained in parallel with the state machine:

private val expressionDisplay = StringBuilder()

Each operator press, open bracket, and close bracket appends to it. AC and = both clear it entirely. The backspace button, when shouldResetInput is true, trims the last operator token back off it so the expression stays consistent with the state.

Private state variables

private var currentInput = "0"       // number currently shown in the main display
private var firstOperand: Double?    // left-hand operand, stored after pressing an operator
private var pendingOp: Char?         // operator waiting to be applied (+, -, *, /)
private var justCalculated = false   // true after = is pressed; next digit starts a fresh calculation
private var shouldResetInput = false // true after operator press; next digit replaces the display

The shouldResetInput flag solves the most common calculator bug: pressing 6, 5, +, 6, 5 would produce 6565 without it, because the display isn't cleared after +.

Currency conversion

All rates from the API are relative to USD (1 USD = X of each currency). Cross-rate conversion is therefore:

val toValue = value * toRate / fromRate
// Example: 100 GBP to EUR, where GBP rate = 1.27, EUR rate = 1.08 (both relative to 1 USD)
// toValue = 100 * 1.08 / 1.27 = 85.04 EUR

The exchange rate label is constructed with full currency names from java.util.Currency:

val fromName = JavaCurrency.getInstance(fromCode).displayName  // e.g. "British Pound Sterling"
val toName   = JavaCurrency.getInstance(toCode).displayName    // e.g. "Euro"
val rateLabel = "1 $fromCode ($fromName) = ${"%.4f".format(toRate / fromRate)} $toCode ($toName)"
// → "1 GBP (British Pound Sterling) = 1.1732 EUR (Euro)"

data/LocalisationData.kt

Static compile-time maps for country-level travel data. Contains three top-level maps:

  • PLUG_TYPES: Map<String, PlugInfo> — plug type string (e.g. "Type G"), voltage, and frequency for ~80 countries
  • TAP_WATER_SAFE: Map<String, Boolean> — whether tap water is generally safe to drink
  • DRIVING_INFO: Map<String, DrivingInfo> — urban/rural/motorway speed limits, BAC limit, alcohol purchase age, and speed unit ("mph" or "km/h")

Also exports COUNTRY_LIST: List<Pair<String, String>> — the curated list of ~80 ISO alpha-2 codes + display names shown in the country picker, and fun plugTypeDescription(type: String): String which expands a plug type code like "Type C/F" into a human-readable description.

Static data is always read directly from these maps at display time, never cached — so app updates take effect immediately without a cache bust.

data/LocalisationRepository.kt

Fetches and caches per-country info from two external APIs, merged with static data:

  • Wikidata SPARQL (query.wikidata.org/sparql) — driving side (P1622) and all emergency numbers (P2852) for the country. Results are returned as label strings via SERVICE wikibase:label.
  • REST Countries (restcountries.com/v3.1/alpha/{code}) — international calling code (idd.root + idd.suffixes[0]), currency names, and official languages.

Both calls fire in parallel with async { } + await(). Results are merged into a CountryLocalisationInfo object, serialised with Gson, and saved to a separate DataStore named "localisation_data" (must not share the delegate with "exchange_rates"). Cache TTL is 7 days.

On network failure the cached value is returned if available; otherwise a stub with only static data is returned and localisationError is set in the ViewModel. Recent country selections (up to 5) are also persisted here as a comma-separated string.

ui/LocalisationScreen.kt

The Local Info screen. Layout: a scrollable column of info cards with a pinned disclaimer footer below the scroll area.

  • Country picker button — shows flag emoji + country name; opens CountryPickerDialog (Dialog + LazyColumn, never DropdownMenu + LazyColumn to avoid nested-scroll crash)
  • Essentials card — emergency numbers, calling code, currency, languages (API data)
  • Driving card — driving side (API), speed limits table with mph/km/h unit from static data, BAC limit ("Zero tolerance" when 0.00%)
  • Practical card — tap water safety (colour-coded), plug type + description + worldstandards.eu link, voltage/frequency, alcohol purchase age

Static fields (plug, tap water, driving) are always read from the bundled maps, not from the cached CountryLocalisationInfo, so Gson's null-for-missing-fields behaviour cannot cause stale or null speed units.

The country picker shows a "Recent" section (last 5 selections) above the full list when not searching. InfoRow uses weight(1f) for the label and weight(2f) for the value, with maxLines = 1, overflow = Ellipsis on the value.

ui/HistoryScreen.kt

A scrollable list of saved conversions (up to 50 entries). Tapping any entry restores the currencies and amount to the calculator. A notes icon on each row opens an edit dialog so the user can label what a conversion was for. History is persisted as a JSON array in DataStore.

ui/SettingsScreen.kt

Appearance (theme, accent colour), haptic toggle, tab visibility, tip percentage default, fuel units, distance pairs, and card profile management. Card profiles are stored as a JSON list in DataStore; each entry carries a name, fee percent, optional minimum fee amount and currency, and a map of per-card custom rates.

ui/CalculatorScreen.kt — Receipt Scanner (OcrOverlayScreen)

The receipt scanner is a full-screen overlay composable (OcrOverlayScreen) launched from the Currency tab. The flow:

  1. Image capture — a camera launcher (rememberLauncherForActivityResult) fires MediaStore.ACTION_IMAGE_CAPTURE. The returned Bitmap is passed to OcrOverlayScreen.
  2. OCR — inside a LaunchedEffect, the bitmap is wrapped in an InputImage and passed to ML Kit's TextRecognition.getClient(). The addOnSuccessListener callback walks the result tree (TextBlock → TextLine → TextElement) and extracts every element whose text parses as a decimal number. Each detection is stored as a DetectedNumber(value, imageBox) — a pixel-space bounding box in the original image.
  3. Currency detection — the same OCR pass scans all element text for currency symbols and ISO codes (£, $, €, ¥, USD, GBP, etc.) using a lookup map. The first match sets detectedReceiptCurrency.
  4. Render — the bitmap is drawn with Image(bitmap) inside a graphicsLayer box that handles pinch-to-zoom and pan via detectTransformGestures. Image coordinates are mapped to screen coordinates using baseScale (fit-to-box scale) and fitOffsetX/Y (letterbox offsets).
  5. Selection overlay — when a detection is tapped (detectTapGestures converts screen → image pixels), it toggles into a selected set. Selected detections render a filled dark box at exactly the bounding-box coordinates, with the converted amount in gold text centred inside — covering the original number. Unselected detections show a faint outline box.
  6. Convert toggle — a chip in the top bar switches between showing converted amounts and raw receipt amounts. When off, the detected receipt currency is used for display. The setting is persisted to DataStore via CalculatorAction.SetOcrConvertEnabled.
  7. Bottom bar — shows the running total of selected items (in receipt currency) and the converted equivalent, plus "Use £…" and "Use $…" buttons that dispatch CalculatorAction.Digit / SetConversionMode events to populate the main calculator.
Why break@outer for currency detection: The detection loop is three levels deep (blocks → lines → elements). Kotlin's forEach lambdas don't support break, so the loops are written as labelled for loops with break@outer to exit all three once a currency symbol is found.

    code.contains(search, ignoreCase = true) || name.contains(search, ignoreCase = true)
}

Filtering matches on both code and name, so searching "pound" finds GBP, EGP, SYP, and others.

Swap button

Between the two CurrencySelector composables sits an IconButton with the SwapHoriz icon (from material-icons-extended). Pressing it dispatches CalculatorAction.SwapCurrencies. The ViewModel swaps the two currency codes and immediately calls saveCurrencyPrefs to persist the new order.

8. How the App Works End-to-End

App launch

  1. Android starts MainActivity.onCreate()
  2. Compose starts rendering CalculatorScreen
  3. The viewModel() call creates a CalculatorViewModel instance
  4. The ViewModel's init block runs:
    • Loads saved currency preferences from DataStore (defaults: EUR to, GBP from)
    • Calls fetchRates(forceRefresh = false)
  5. fetchRates calls repository.getRates("USD", false), which checks the cache:
    • Cache < 24h old → deserialise and return immediately
    • Cache stale → fetch from open.er-api.com, update cache, return
    • Offline and cache exists → return stale cache silently
    • Offline and no cache → lastUpdated is set to "Offline"
  6. ViewModel updates _uiState with the rate map, sorted currency list, and timestamp
  7. The StateFlow emits the new state; Compose recomposes the screen

User presses a digit

  1. Button's onClick calls vm.onAction(CalculatorAction.Digit(7))
  2. onAction routes to handleDigit(7)
  3. If shouldResetInput or justCalculated is true, currentInput is replaced; otherwise the digit is appended (up to 12 characters)
  4. updateDisplay() rebuilds the expression string from expressionDisplay and emits a new CalculatorUiState
  5. updateCurrencyDisplay() recalculates both converted amounts and the rate label, emitting another state update
  6. Compose redraws only the affected composables

User presses an operator

  1. handleOperation('+') is called
  2. If shouldResetInput is already true (operator chaining), the pending operator symbol in expressionDisplay is replaced in-place
  3. Otherwise, if there is already a pending operation, it is evaluated first: firstOperand = applyOp(firstOperand, current, pendingOp)
  4. firstOperand now holds the left-hand value; pendingOp stores the operator character
  5. The operator symbol is appended to expressionDisplay
  6. shouldResetInput = true — the next digit will replace the display rather than append

User presses ( )

The smart bracket button checks context before acting:

  • Open — if shouldResetInput is true (just pressed an operator) or the state is completely fresh: push BracketState(firstOperand, pendingOp) onto the stack, reset inner state, append ( to the expression
  • Close — if there are open brackets: resolve the inner expression, pop the stack to restore the outer operator, apply that operator to the bracket result, set shouldResetInput = true
  • Nothing — mid-number entry with no open brackets: the button is ignored

User presses =

  1. handleCalculate() evaluates any remaining pending operation on currentInput
  2. If there are unclosed brackets on the stack, they are resolved in reverse order (auto-close)
  3. currentInput is set to the final formatted result
  4. All state is reset: firstOperand = null, pendingOp = null, bracketStack.clear(), expressionDisplay.clear()
  5. justCalculated = true — the next digit starts a fresh calculation rather than appending to the result

User scans a receipt

  1. User taps the camera icon on the Currency tab → cameraLauncher.launch(uri) fires
  2. Android camera app captures an image and returns a Bitmap
  3. OcrOverlayScreen is shown with the bitmap; a LaunchedEffect passes it to ML Kit
  4. ML Kit processes the image on-device (no network call) and returns a Text result tree
  5. The app parses detected elements: numbers → DetectedNumber list; symbols → detectedReceiptCurrency
  6. Compose renders bounding-box overlays on the image; user taps a price to select/deselect it
  7. Selected prices accumulate in a running total shown in the bottom bar
  8. Tapping "Use £…" dispatches the total as digit inputs to the main calculator state machine

9. Building and Installing Manually

Prerequisites

  • JDK 17: sudo apt install openjdk-17-jdk
  • Android SDK at ~/android with platform-tools, platforms;android-35, build-tools;35.0.0
  • local.properties containing sdk.dir=/home/rich/android

Build commands

# Debug build (signed with a debug key — installs on any device with debugging enabled)
cd ~/calcApp
./gradlew assembleDebug

# Output
app/build/outputs/apk/debug/app-debug.apk

# Clean build (use if you hit strange caching issues)
./gradlew clean assembleDebug

# See all available tasks
./gradlew tasks

Installing via ADB over WiFi

Requirements: phone and laptop on the same network, Developer Options enabled, Wireless Debugging enabled.

# Step 1: Pair (one-time per ADB server instance)
# Get pairing IP:port and 6-digit code from phone:
# Settings → Developer Options → Wireless Debugging → Pair device with pairing code
~/android/platform-tools/adb pair 192.168.x.x:<pair-port> <6-digit-code>

# Step 2: Connect (use the port on the main Wireless Debugging screen, not the pairing port)
~/android/platform-tools/adb connect 192.168.x.x:<connect-port>

# Step 3: Install (-r replaces existing install)
~/android/platform-tools/adb install -r app/build/outputs/apk/debug/app-debug.apk

# Verify device is connected
~/android/platform-tools/adb devices

# View live logs
~/android/platform-tools/adb logcat
Pairing code note: Pairing codes expire in about 60 seconds. Have your ports and code ready before running the pair command. After successful pairing, the connect step persists as long as you don't kill the ADB server. The connect port (shown on the main Wireless Debugging screen) is different from the pairing port.

WSL2-specific notes

USB ADB doesn't work natively in WSL2 because WSL2 runs as a VM. Options:

  • WiFi ADB (recommended) — works natively as long as phone and PC are on the same subnet
  • usbipd-win — USB passthrough from Windows to WSL2; can be unreliable if Windows software (e.g. Samsung Smart Switch) holds the device

The Samsung-specific udev rule at /etc/udev/rules.d/51-android.rules (vendor ID 04e8) grants permission for USB ADB should you use the USB path in future.

10. How to Extend the App

Adding a new calculator operation (e.g. square root)

  1. Add object SquareRoot : CalculatorAction() to the sealed class in CalculatorViewModel.kt
  2. Add a handleSquareRoot() private function that reads currentInput, computes the result, and sets currentInput = formatResult(result)
  3. Add a case in the onAction() when block: is CalculatorAction.SquareRoot -> { handleSquareRoot(); updateDisplay() }
  4. Add a BtnDef("√", ButtonLight, Color.Black, CalculatorAction.SquareRoot) entry in the appropriate row of ButtonGrid in CalculatorScreen.kt

Changing the exchange rate API

Only ExchangeRateApi.kt needs to change. The repository, ViewModel, and UI are all isolated from the API details — they only see Map<String, Double>. If the new API uses a different base currency, update the getRates("USD", ...) call in CalculatorViewModel.fetchRates() and the cross-rate formula in updateCurrencyDisplay().

Adding a third currency column

  1. Add val extraCurrency: String and val extraAmount: String to CalculatorUiState
  2. Add data class SetExtraCurrency(val code: String) : CalculatorAction()
  3. Extend updateCurrencyDisplay() to compute and emit the extra amount alongside the existing two
  4. Add a third CurrencySelector and a third amount Text in CalculatorScreen

Adding a calculation history screen

  1. Add val history: List<String> to CalculatorUiState
  2. Append the expression and result to it in handleCalculate() before clearing state
  3. Create a HistoryScreen.kt composable that renders the list
  4. Add navigation — the simplest approach is Jetpack Navigation Compose (androidx.navigation:navigation-compose)

Persisting calculation history across sessions

DataStore works well for simple key-value data but is awkward for a growing list. For calculation history, consider Room (Android's SQLite ORM). Add the Room dependency, create an Entity data class, a Dao interface, and a Database class. The repository pattern already isolates the rest of the app from storage details — add a HistoryRepository alongside the existing ExchangeRateRepository.
